## Executive Summary

Today, the average time between an attacker compromising a FICO cloud account and an incident being fully created and response procedures initiated ranges from **10 to 50+ hours** - as observed during a previous large-scale cloud adversary simulation conducted by the Red Team. Our SOC operates 24/7 and triages alerts effectively, often within 20-50 minutes. However, the early-phase signals generated by attacker reconnaissance - enumeration calls, role assumptions, and identity behavior that resembles normal operations - are not classified as critical severity. These alerts compete with routine noise from legitimate identity activity, contributing to alert fatigue. Even when the SOC identifies and escalates early, the standard procedure requires contacting the account owner and responsible team to confirm whether the activity is legitimate - a process that alone can add hours or days to the response timeline. The net result: the attacker operates freely during the reconnaissance and initial access phases while the organization waits for human confirmation loops to complete.

**Cloud Deception** eliminates this gap by placing realistic honeypot resources across our 100+ AWS accounts that act as tripwires during the attacker's reconnaissance phase. When an attacker interacts with any lure - even a single API call - we receive an alert within **5-15 seconds** with zero false positives. No owner confirmation needed - no legitimate user should ever touch these resources, making every alert an immediate true positive that warrants containment action.

**POC Results:**
- 19 deception scenarios covering secrets, credentials, databases, containers, IAM roles, and infrastructure
- Detection latency: **8-12 seconds** (vs. 10+ hours today)
- False positive rate: **zero** - no legitimate user or automation touches these resources
- Total cost: **under $150/month** for the entire organization (100+ accounts, monitoring + decoy resources)

**The shift:** We move from reactive incident response (detect after exfiltration) to proactive threat detection (detect during reconnaissance, before any real data is touched). Every deception alert is a confirmed true positive that warrants immediate investigation.

## 1. The Gap

### The Detection Time Problem

Our current security tooling (Wiz, GuardDuty, Security Hub) monitors for misconfigurations, known attack signatures, and policy violations. These tools work — but the early-phase signals they generate during attacker reconnaissance (enumeration calls, role assumptions, identity behavior that resembles normal operations) are not classified as critical severity. The SOC operates 24/7 and triages these alerts within 20-50 minutes, but the standard process requires contacting the account owner and responsible team to confirm whether the activity is legitimate — a step that alone can extend the response timeline to **10-50+ hours**.

**Why this happens:** Attacker recon looks identical to normal identity behavior. `AssumeRole`, `GetParameter`, `DescribeKey` — these are calls that legitimate users and automation make thousands of times daily. The alerts they generate are low-to-medium severity, compete with routine noise, and don't warrant immediate containment without owner confirmation.

### Why Existing Tools Don't Catch This

| Tool | What It Detects | What It Misses |
|------|----------------|----------------|
| **Wiz** | Misconfigurations, vulnerabilities, exposed resources, compliance drift | Post-compromise activity using valid credentials - attacker looks like a legitimate user |
| **GuardDuty** | Known attack patterns (crypto mining, DNS exfil, unusual API volume) | Low-and-slow enumeration, targeted secret reads, role chaining with valid permissions |
| **Security Hub** | Compliance failures, CIS benchmarks, best practice violations | Real-time attacker activity - it's a posture tool, not a detection tool |
| **CloudTrail** | Logs everything - but logging ≠ detection | Nobody is watching the logs in real time for specific resource-targeted access patterns |

**The gap is not visibility - it's time-to-detect.** We have the logs. We have the tools. But detection happens after the damage is done because our current approach waits for abuse indicators (data exfiltration, resource modification, anomalous billing) rather than catching the attacker during their reconnaissance phase.

### What Cloud Deception Changes

Cloud deception flips the model from **reactive** to **proactive**:

- We place a mesh of realistic-looking lure resources across the attack surface
- These lures sit in the path an attacker naturally follows during reconnaissance
- When the attacker interacts with a lure - even just reading a secret or assuming a role - we get an immediate, high-confidence alert
- Detection moves from the **exfiltration phase** (10+ hours) to the **recon phase** (minutes)
- Every alert is a true positive - no legitimate user or automation should ever touch these resources

| Metric | Current (Reactive) | With Deception (Proactive) |
|--------|-------------------|---------------------------|
| Time to detect & respond | 10–50+ hours (alert fatigue + owner confirmation loops) | **5-15 seconds** (immediate true positive) |
| Detection phase | After exfiltration/abuse | During reconnaissance |
| False positive rate | High (tuning required) | **Zero** (true positive by design) |
| Attacker awareness | Unaware they've been detected | Unaware they hit a tripwire |
| Response posture | Reactive - contain damage | Proactive - prevent damage |

### The Attacker's Advantage

An attacker with valid credentials can:
- Assume IAM roles and pivot across services
- Read secrets, parameters, and database records
- Download S3 objects (Terraform state, SSH keys, compliance reports)
- Pull container images with embedded credentials
- Modify security groups and start instances

All of these actions generate CloudTrail events - but nobody is watching for them in real time.

### What's at Risk

Beyond human identities, our AWS accounts contain a broad range of machine identities and service principals - Lambda execution roles, EC2 instance profiles, ECS task roles, CI/CD pipeline roles, cross-account trust roles, and third-party integration roles (Wiz, Datadog, monitoring agents). Any of these identities, if compromised or misconfigured, can be used to access resources across the account. An attacker who gains access through any identity - human or machine - follows the same reconnaissance pattern: enumerate what's available, identify high-value targets, and exfiltrate. Deception lures sit in the path of this reconnaissance regardless of which identity the attacker is operating under.

### Our Identity Center Roles

Our AWS Identity Center (SSO) grants four permission sets. The most commonly used role - **GTS-ReadOnly** - already has permissions to interact with every deception scenario:

| Permission Set | Usage | Can Trigger Deception Scenarios |
|---------------|-------|-------------------------------|
| **GTS-ReadOnly** | Most used (daily access for all teams) | ALL 19 scenarios - has `secretsmanager:Get*`, `ssm:Get*`, `s3:Get*`, `dynamodb:Scan/Query/GetItem`, `sqs:ReceiveMessage`, `logs:GetLogEvents/FilterLogEvents`, `kms:Describe*`, `ecr:BatchGetImage`, `lambda:Get*`, `cloudformation:Describe*` |
| **GTS-PowerUser** | Developers (cannot AssumeRole or modify IAM) | 17 of 19 scenarios - has all data access but cannot assume lure roles directly |
| **GTS-Admin** | Limited admins (full access with guardrails) | ALL 19 scenarios |
| **GTS-FullAdmin** | Rarely granted (unrestricted `*:*`) | ALL 19 scenarios |

**Key insight:** The GTS-ReadOnly role - used by the majority of staff - has `sqs:ReceiveMessage`, `dynamodb:Scan`, `secretsmanager:Get*`, and `s3:Get*` on `Resource: "*"`. This means any compromised ReadOnly session can access every decoy resource. However, no legitimate ReadOnly user should ever call `GetSecretValue` on `prod/payment-gateway/stripe-keys` or `Scan` on `prod-customer-profiles` - these are resources that don't exist in normal workflows.

**This is exactly why deception works:** The permissions exist, but the intent to use them on specific decoy resources is the signal. A legitimate ReadOnly user lists secrets (normal) - but never reads a specific payment secret by name (attacker behavior).

**Note on GTS-PowerUser:** This role explicitly denies `sts:AssumeRole`, so it cannot assume lure roles directly. However, it can still access decoy resources (S3, Secrets Manager, SSM, DynamoDB, etc.) through its broad data-plane permissions. Scenarios 2, 3, 9, 10, 11, 13 would still trigger if a PowerUser session directly accesses decoy resources without going through the lure role first.

## 2. Proposed Solution

### Cloud Deception - Honeypot Infrastructure at Scale

Deploy realistic-looking decoy resources across 100+ AWS accounts that:
- **Look like production infrastructure** - realistic names, proper tagging, real-looking data
- **Attract attacker interaction** - secrets named `prod/payment-gateway/stripe-keys`, roles named `payment-secrets-readonly-role`, tables named `prod-customer-profiles`
- **Generate high-fidelity alerts** - any interaction is a confirmed true positive (no legitimate user should touch these)
- **Alert in real time** - seconds, not hours

### How It Works

│  ATTACKER ENTERS ACCOUNT                                    │
│  (compromised creds, insider, lateral movement)             │
│                                                             │

│  • IAM roles with enticing names                            │

### Detection Strategy

| What We Monitor | Why |
|----------------|-----|
| `AssumeRole` on 22 lure roles | No legitimate user should assume these - true positive by definition |
| Resource-specific API calls on exact decoy ARNs | If someone calls `GetSecretValue` on our fake secret, they found the lure |

| What We Exclude | Why |
|----------------|-----|
| `ListBuckets`, `ListSecrets`, `ListTables`, etc. | Legitimate automation (Config, Security Hub, SSO) makes these constantly - would generate 100% false positives |

### Severity Model

| Severity | Meaning | Events |
|----------|---------|--------|
| **CRITICAL** | Attacker is actively extracting data from a decoy resource | GetSecretValue, GetObject, Scan, Query, Decrypt, ReceiveMessage, etc. |
| **HIGH** | Attacker assumed a decoy role (entry point confirmed) | AssumeRole, AssumeRoleWithSAML |

## 7. Account Owner Communication & Coordination

Deception resources are deployed into accounts owned by other teams. To maintain trust and avoid confusion, account owners will be informed and given a technical point of contact.

### Process

1. **Pre-deployment notification:** Before deploying deception scenarios to any account, the designated technical point of contact for that account will be informed by CSC.
2. **Decoy resource list:** Each account's technical point of contact will receive the full list of decoy resource names deployed in their account (role names, bucket names, secret paths, table names, etc.).
3. **Do-not-touch guidance:** Account owners will be advised that these resources are managed by CSC, should not be modified or deleted, and that any interaction will generate a security alert.
4. **Escalation path:** If an account team needs to modify infrastructure that conflicts with a decoy resource, they contact CSC to coordinate removal or renaming.
5. **Confidentiality:** The decoy resource list is shared only with the designated technical point of contact — not broadly distributed — to preserve the deception's effectiveness against insider threats.

### Why This Matters

- Prevents accidental deletion of decoy resources during account maintenance
- Ensures account teams don't waste time investigating "unknown" resources
- Maintains trust between CSC and account-owning teams
- Provides a clear escalation path if conflicts arise

## 9. Key Takeaways

1. **Zero false positives** - Unlike traditional detection, deception alerts are true positives by design. No tuning required.

2. **Near real-time** - 5-15 second detection latency vs. hours/days for log-based detection.

3. **Negligible cost** - ~$0.06/month for the monitoring stack across 100+ accounts. Scenario resources cost ~$1.25-$3.70/account depending on selection.

4. **Zero maintenance** - StackSets auto-deploy to new accounts. No signature updates, no rule tuning, no model training.

5. **Covers the blind spot** - Detects post-compromise activity that Wiz, GuardDuty, and Security Hub cannot see (legitimate API calls with valid credentials).

6. **Scalable** - Same architecture works for 10 accounts or 1,000 accounts with no changes.
