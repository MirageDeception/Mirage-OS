# Scenario 4 — S3 SSH Key → EC2 Lure Bastion with Sensitive Files

## Prompt

Create a deception scenario called `scenario-4` using CloudFormation template.

**Important**: Do NOT use `FAKE`, `EXPIRED`, `REVOKED`, or `REDACTED` in any key names,
values, labels, or content. All credentials and data must look legitimate and usable to
maximize attacker engagement.

### Deception Chain Overview

```
Attacker
  │
  ├─► Discovers IAM Role: devops-s3-deploy-role
  │     (assumable by any principal in the account)
  │
  ├─► Assumes role ─► gains S3 read access
  │
  ├─► Finds S3 Bucket: devops-deploy-keys-<account-id>
  │     └─► Downloads SSH private key: keys/prod-bastion-keypair.pem
  │
  ├─► Uses SSH key to connect to lure EC2 instance (prod-bastion-host)
  │     └─► Instance has sensitive files on disk:
  │           ├─► /home/ec2-user/.env — DB creds, API keys
  │           ├─► /home/ec2-user/config/db-backup-creds.json — DB backup credentials
  │           ├─► /home/ec2-user/.ssh/internal-hosts.conf — internal host list
  │           └─► /root/.aws/credentials — AWS credentials placeholder
  │
  └─► Attacker attempts to use credentials ─► triggers alerts
```

### Lure Resources

- **IAM Role**: Named `devops-s3-deploy-role` with permissions:
  - `s3:ListAllMyBuckets`
  - `s3:ListBucket` — scoped to the lure bucket
  - `s3:GetObject` — scoped to the lure bucket
  - `ec2:StartInstances` — scoped to the lure instance
  - `ec2:ModifyInstanceAttribute` — scoped to the lure instance
  - `ec2:DescribeInstances`
  - `ec2:DescribeSecurityGroups`
  - `ec2:AuthorizeSecurityGroupIngress` — scoped to the bastion security group
  - `ec2:RevokeSecurityGroupIngress` — scoped to the bastion security group
  - `sts:AssumeRole` in trust policy by anyone in this account (root principal)

- **S3 Bucket**: Named `devops-deploy-keys-<account-id>`
  - Contains a real SSH private key (`keys/prod-bastion-keypair.pem`) generated during deployment
  - Bucket policy allows read from account root principal (not public)
  - Full security best practices (encryption, versioning, public access block, TLS-only)

- **EC2 Instance**: Named `prod-bastion-host`
  - Amazon Linux 2023 AMI, t3.nano
  - Security group allows SSH (port 22) from deployer-specified CIDR (default 165.225.0.0/24)
  - Attacker must modify the security group to add their own IP before SSH
  - UserData seeds sensitive-looking files onto the instance filesystem
  - Instance is deployed in STOPPED state — attacker must start it
  - Instance has NO instance profile by default — scenario-5 can attach one later

- **Deploy script prompts for**:
  - VPC selection (lists all VPCs with names)
  - Subnet selection (lists subnets in chosen VPC)
  - SSH allowed CIDR (default: 165.225.0.0/24)
