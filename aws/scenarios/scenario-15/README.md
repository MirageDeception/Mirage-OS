# Scenario 17 — SAML Provider Lure: Fake Okta SSO Integration

## Deception Story

An attacker who gains access to the AWS account discovers an IAM role named
`sso-audit-readonly-role` — assumable by any principal in the account. The
role grants read-only access to SAML providers and IAM roles.

The attacker lists SAML providers and finds `ProdOktaSSO`. Downloading the
SAML metadata reveals the Okta entity ID, SSO URL, and X.509 signing
certificate. Listing IAM roles filtered by SAML trust reveals two high-value
targets:

- `prod-okta-admin-role` with AdministratorAccess
- `prod-okta-developer-role` with PowerUserAccess

Both roles require a valid SAML assertion from the Okta IdP to assume. Any
attempt to assume them directly or forge a SAML assertion triggers detection.
The Okta endpoint and entity ID serve as breadcrumbs that lure the attacker
into further reconnaissance against the identity provider.

## Deception Chain

```
Attacker
  │
  ├─► Discovers IAM Role: sso-audit-readonly-role
  │     (assumable by any principal in the account)
  │
  ├─► Assumes role ─► gains iam:ListSAMLProviders, iam:GetSAMLProvider,
  │                    iam:ListRoles, iam:GetRole
  │
  ├─► Lists SAML providers → finds ProdOktaSSO
  │
  ├─► Gets SAML metadata → extracts:
  │     ├─► Entity ID: http://www.okta.com/exk1prod2abc3def4
  │     ├─► SSO URL: https://acme-corp.okta.com/app/amazon_aws/.../sso/saml
  │     └─► X.509 signing certificate
  │
  ├─► Lists roles with SAML trust → finds:
  │     ├─► prod-okta-admin-role (AdministratorAccess)
  │     └─► prod-okta-developer-role (PowerUserAccess)
  │
  └─► Attempts to assume SAML role or access Okta endpoint → triggers alerts
```

## Security Best Practices Applied

- IAM discovery role: trust policy scoped to account root principal (not public)
- SAML-trusted roles require valid SAML assertion with `SAML:aud` condition
- SAML-trusted roles cannot be assumed via `sts:AssumeRole` (only `sts:AssumeRoleWithSAML`)
- Self-signed certificate is generated fresh during deployment (no shared keys)
- No cross-account access
- No real Okta integration — all endpoints are non-functional
