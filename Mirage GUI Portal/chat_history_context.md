## Chronological Development Milestones

### Act I: The PoC Review & Hub Validation (June 20, 2026)
- **User Intent:** The user presented an early Proof-of-Concept stored in `aws native solution/csc-prod/` (`monitoring-brain.yaml`, `detection-rules.yaml`, `deploy.sh`) to build an automated deception SaaS.
- **Architectural Discovery & Crisis:**
  - Auditing `detection-rules.yaml` revealed that the PoC deployed 19 static scenario rules directly onto the central Hub EventBus, with hardcoded decoy names like `infra-s3-data-readonly-role`.
  - In an enterprise with 50 Spoke accounts, the Hub would require continuous stack updates every time any account changed a decoy name.
  - The Python Lambda contained hardcoded scanner whitelists (`WizScanner-Role`, `WizAccess-Role`) and old PoC account IDs (`913511275171`).
- **The Dual-Tier Architecture Agreement:**
  - We agreed to discard `detection-rules.yaml` in the Hub.
  - **Hub:** Only hosts 14 static, service-level rules listening for sensitive API calls (`s3:GetObject`, `secretsmanager:GetSecretValue`, `sts:AssumeRole`).
  - **Spoke:** Dynamically filters on exact decoy names, forwarding only true decoy hits to the Hub.
- **Hub Deployment Hurdles:**
  - Fixed an IAM trust failure caused by a trailing dot in the role name (`MiragePlus-Hub-Deployment-Role.`).
  - Fixed a Node.js subprocess scoping bug (`process1`) in `src/app/api/deploy-brain/route.ts` that caused `deploy-hub.sh` to fail silently.
  - Installed missing macOS `awscli` dependencies via Homebrew.
  - Validated end-to-end deployment of the Monitoring Brain stacks (`deception-v2-monitoring-brain` and `deception-v2-service-rules`).

### Act II: Catalog Evolution & The Contextual Variables Migration (June 25 – July 15, 2026)
- **User Intent:** Build a web portal allowing security teams to select Honey Attack Paths and deploy them into Spoke accounts.
- **The Initial Fragile Approach (Markdown Parsing):**
  - The catalog UI was initially generated by scanning `details.md` files for bolded strings (`**S3 Bucket**`, `**IAM Role**`).
  - `/api/deploy-spoke` attempted regex string replacements on `main.tf` files to inject custom decoy names.
- **The Crash on Scenarios 6–19:**
  - Scenarios 6 through 19 had inconsistent markdown formatting without standard headers.
  - String replacement broke Terraform syntax and failed completely when a scenario had multiple resources of the same type (e.g., Scenario 8 with three IAM roles).
- **The Architectural Migration:**
  - We abandoned markdown parsing entirely.
  - Standardized all 19 scenarios on native **Contextual Variables**:
    - `var.discovery_resource_name` (initial bait)
    - `var.execution_resource_name` (pivot role/compute)
    - `var.target_resource_name` (sensitive datastore)
  - Refactored `/api/scenarios/route.ts` to parse `variables.tf` directly to generate UI forms.
  - Refactored `/api/deploy-spoke/route.ts` to pass `-var` flags natively to `terraform apply`.

### Act III: The EventBridge Engine, Quota Limits & Teardown Drift (July 19 – July 23, 2026)
- **User Request (Step 4090–4096):** *"where are you maintaing this history like is there any file created for that where you are mainting it ? also i cant see a section in history for trust policy, add that"*
  - Implemented `db_history.json` and added the `trust_policy_update` action type to the audit trail.
- **User Request (Step 4111):** *"theres one more issue, click on compare button, the UI gets unstable, can you fix that, refer ss"*
  - Discovered that trailing commas in JSON comparison were causing false-positive additions/removals (+8/-2 instead of +6). Stripped trailing commas before computing the diff summary.
- **User Request (Step 4128):** *"in update available button remove the wordings, only keep the symbol. will i be able to see in history what scenario is teared down"*
  - Simplified the button to a clean warning icon `⚠️` and enriched history entries with `scenarioId` and `scenarioName`.
- **User Request (Step 4140):** *"hey i deleted scenario 7, it deleted the rule from the portal but in aws it wasnt deleted and the trust policy was also not updated"*
  - **The Two-Step Deletion Bug:** AWS forbids deleting an EventBridge rule that has attached targets. Refactored `/api/delete-rule` to execute `RemoveTargetsCommand` before `DeleteRuleCommand`.
  - **Teardown Drift (The "Receipt Book" Problem):** Deleting a scenario from a grouped rule left ghost decoys in AWS. We expanded `db_inventory.txt` from 4 columns to 5 (`AccountId | ScenarioId | RuleName | DecoyName | Category`), enabling the backend to look up the exact resources by `ScenarioId`, strip them from the JSON pattern, recalculate the `source` array, and set status to **Update Available ⚠️**.
  - **Trust Policy Auto-Sync:** Integrated AWS IAM SDK into `/api/deploy-rule` to dynamically read `AssumeRolePolicyDocument` and append new rule ARNs to `aws:SourceArn`.
- **The Missing Outputs Crisis:**
  - Audited all 19 scenarios and discovered that 14 scenarios lacked `output "decoy_resources"`, causing the rule compiler to silently fail. Created the mandatory JSON output contract.
- **Secrets Manager Lockup:**
  - Scenario 2 re-deployment hung permanently because AWS Secrets Manager keeps deleted secrets in a 7–30 day recovery window. Added `force_delete_without_recovery = true` and `recovery_window_in_days = 0` to all secret resources.
